## 1. 背景与问题

**要解决的不是「缺一个页面」，而是：读完 RAG 文档的人无法验证自己是否真的理解，讲解的人也无法指着某个环节说「问题就出在这一步」。**

依据（均为已核实的事实）：

- RAG 知识已以文档形式存在：`knowledge/一文完全读懂RAG.md`（1352 行），覆盖三段式主线、分块、BM25、Query 改写、粗筛与精排。
- 该文档第九节有一个能跑通的实战 demo，但有环境门槛：需要 Python + langchain + pymilvus + 本地 embedding 模型 + LLM 密钥。换机器要重装，现场依赖外部模型服务与网络。
- 工作区已有一个真实检索实现 `dsh-plugin-starter/xhs-rag/`（纯关键词、无 embedding、带 `degraded` 降级标记），它的能力上限正好可作为「真实世界的约束」参照。

**v0.4 追加的问题陈述**：光有流程可视化还不够 —— 观众看完未必相信「RAG 到底带来了什么价值」。
因此本版把**同一个问题、同一个模型、只差「有没有把收藏喂给它」**的两段回答并排放在首屏，用可核对的差异证明价值。

**用户视角的问题陈述**：我想搞懂 RAG，但现有材料要么是纯文字（读完记住了名词，不知道数字从哪来），要么是需要装半小时环境的脚本（跑起来了但不知道中间发生了什么）；而且我说不出「用了 RAG 之后它到底好了多少」。

## 2. 目标与衡量指标

**说明**：本次没有线上流量，指标全部是**当场可观察的行为量**。基线一律为「无」（新建页面）。

### G1 全链路可演示
- **指标**：断网双击打开，从 12 条语料走到 7 条预置 / 边界 query 全部有明确结果态的过程中，控制台报错数与白屏次数
- **目标**：0 报错、0 白屏；7 条 query 100% 有明确结果态
- **v0.4 实测**：核心 81 项 + UI 冒烟 39 项全部通过；页内自检 23/23 PASS

### G2 标记可被辨识（行为指标）
- **指标**：找一个没读过本文档的人，只看页面，**能正确指认「哪些环节是模拟 / 混合来源」的比例**
- **目标**：≥ 2/3 的 🔶 环节被正确指认
- **验证方式**：演示后当场提问
- **注**：v0.3 的「9 个环节标记覆盖率 100%」降为交付检查项（AC-19）

### G3 教学有效性【v0.4 取消页内手段】
- v0.3 用「5 道理解题」当场收数；v0.4 按 D17 删除理解自测，**页内不再有 G3 的采集手段**。
- 替代做法：用「有 RAG / 无 RAG 对照」当场口头问一句「这两栏差在哪」，把注意力引到**价值差异**而不是术语记忆上（记入 G5）。
- 诚实边界：3 人样本只能作为方向性信号，**不能**当作教学效果的证据（R4）。

### G4 误导率为零（负向指标）
- **指标**：观众中「以为 🔶 环节是真算出来的」「以为 ⑨ 是当场调用模型」的人数
- **目标**：0 人
- **埋点缺口**：G4 无法用埋点支撑，只能演示后口头确认

### G5 价值差异可核对（v0.4 新增）
- **指标**：观众能否在 30 秒内说出「有 RAG 那栏比无 RAG 那栏多出了什么」
- **目标**：能看到「具体帖子 / 具体数字 / 可点出处 / 主动提示不可信内容」这 4 项中的 ≥ 3 项
- **验证方式**：演示后当场提问；页面上的「对照小结」作为参考话术

## 3. 目标用户与使用场景

| 角色 | 描述 | 他要什么 |
|---|---|---|
| A（主要） | 我 / 同组同学，读过文档但概念模糊 | 每个环节的输入输出都看得见，能上手改 |
| B | 要给别人讲 RAG 的人 | 投屏时能一步步点，且**不怕被问住**（边界要写在页面上） |
| C（**不是**本 demo 的服务对象） | 小红书普通用户 | 本页面不做收藏管理、不做真实抓取的产品化 |

**场景 1（讲解）**：投屏，从「我的问题」开始点一个预置 query，先看首屏两栏对照，再展开 ⑥⑦ 讲 BM25 的词频饱和与文档长度归一化。

**场景 2（自习）**：把预置 query 换成自己想要的，看某个词为什么没召回（④⑤ 里有逐词的 df / IDF / 倒排表）。

**场景 3（对照）**：把 query 从 `上海有什么好吃的` 换成 `雪山索道`，看到「宽松命中」回来的结果其实不相关 —— 建立「召回与准确是权衡关系」的直觉。

**场景 4（收藏整理）**：用 `整理我的收藏夹` 看全库聚合，理解「query 提及收藏时同样走 RAG 引用」。

**不在场景内**：多用户协作、服务端持久化、移动端浏览。

## 4. 功能需求

### 4.1 范围界定

**In Scope（本次做）**

- 单个自包含 HTML，双击即开，离线可用，**不发任何网络请求**
- 能力 1：`语料 → 分块 → 分词 → 建索引` 全过程可见（合并为「预处理」折叠模块）
- 能力 2：`问题 → 意图与检索词 → 打分排序 → 双份 Prompt → 决策建议（有 RAG / 无 RAG）` 全过程可见
- **每个环节的真实/模拟标记 + 页面顶部图例**（FR-11）
- 7 条预置 / 边界问题一键填入（FR-13）
- 页内事件面板，可导出 JSON（FR-12）
- **有 RAG / 无 RAG 对照**（FR-14）与**真实 LLM 产出 + prompt 校验**（FR-15）
- 每个模块可展开/收起，解释文案收进 ⓘ 说明符号（FR-16）

**Out of Scope（明确不做，评审时不必问）**

- ❌ **不做真实抓取**：不连小红书、不展开短链、不发任何网络请求
- ❌ **不做真实 embedding / 向量检索**：页面上没有任何向量相关展示
- ❌ **不做实时模型调用**：⑨ 的回答是提前生成后内嵌的（页面写明「不是当场调用」）
- ❌ **不做混合检索对比**（关键词 vs 向量并排）
- ❌ **不做收藏库的增删改与持久化**：刷新回到初始 12 条
- ❌ **不做检索效果评估**（RAGAs 四指标）
- ❌ **不做理解自测 / 测验**（v0.4 删除）
- ❌ **不做移动端适配**：只要窄窗口下布局不重叠即可
- ❌ 不做多语言、不做深色模式
- ❌ **不承诺与 `xhs-rag` 插件行为一致**（R1）

### 4.2 真实性对照表（本 PRD 最重要的一节）

**四类标记**（页面顶部图例逐条解释）：

| 标记 | 含义 |
|---|---|
| ✅ 真实 | 结果由页面**当场计算**，可人工复算 |
| ✅ 真实 LLM 产出 | **真实模型输出**，用页面同一份 prompt 离线预生成后内嵌；`promptSha` 校验一致才展示 |
| 🔶 模拟 | 结果是预置内容 / 用规则近似 LLM |
| 🔶 混合来源 | 打分本身是真算的 BM25，但参与打分的词**有一部分来自模拟的改写环节**；页面逐词标出来源 |

| # | 环节 | 演示里做什么 | 判定 | 依据 / 理由与实测 |
|---|---|---|---|---|
| ③ | 分块 | 按段落/标点优先级切块，参数可调 | ✅ 真实 | 纯字符串处理。**实测**：正文中位数 168 → `chunkSize=84`、`overlap=17`；N=34；保真 12/12；10/12 条 ≥2 块 |
| ④ | 分词 | CJK 单字 + 相邻双字；拉丁词 ≥2 | ✅ 真实 | 与 `search.js:24-49` 一致。**新增查询侧规则**：丢弃「含功能字」的 bigram（表刻意很窄，`上海` 不受影响） |
| ⑤ | 建索引 | df / avgdl / 倒排表 | ✅ 真实 | 全量语料在页面内。**实测**：词典 1688、Σ\|D\|=2160、avgdl=63.529 |
| ⑥ | 意图识别与检索词构建 | 意图分类 + 原词/改写词/主题词 | 🔶 模拟 | 文档 337–361 行明确说这是**生成任务、要过 LLM**；本页用规则 + 预置映射近似 |
| ⑦ | 检索与打分 | 真算 BM25，三遍策略 | 🔶 混合来源 | 公式来自文档 192–223 行。**为什么不是纯 ✅**：参与打分的词含 ⑥ 的产出（见下） |
| ⑧ | Prompt 组装 | 拼出**两份** prompt 全文并展示、可复制 | ✅ 真实 | 纯字符串拼接；两份 prompt 各自带 hash，供 ⑨ 校验 |
| ⑨ | 决策建议与出处 | 有 RAG / 无 RAG 两栏 + 可点引用 | ✅ 真实 LLM 产出 | 模型输出，离线内嵌；**不显示任何置信度 / 相似度数字**；校验失败退回 🔶 模板并标注 |

**统计**：7 个环节 = **4 个 ✅ 真实**（③④⑤⑧）+ **1 个 ✅ 真实 LLM 产出**（⑨）+ **1 个 🔶 模拟**（⑥）+ **1 个 🔶 混合来源**（⑦）。

#### ⑦ 为什么是「混合来源」（v0.4 关键口径）

原 v0.3 的规定（D11）是：打分只用 query 原词，⑥ 的三分类**不参与打分**，好处是 ⑦ 可以标「✅ 真实」。
但这样「国庆节去哪儿玩」在收藏里必然 0 命中，agent 就答不出生活化的问题。

v0.4 按用户要求让改写词参与检索，并按 4.2 ⑥ 当初预留的口径处理：

> 若要改为参与打分，则 ⑦ 必须改标为「🔶 混合来源」。

**处置**：⑦ 标为混合来源，并在每条结果里**逐词标出来源**（原词 / 改写 / 主题）与贡献分。
**这不是把模拟说成真实，而是把来源摊开给观众看**（代价见 R7）。

#### ⑦ 的算法口径

- **文档 D = chunk 文本，单字段。标题不参与打分**（标题命中只在结果层展示），不引入 BM25F。
- **公式**：

  ```
  IDF(t)      = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))       N = chunk 总数
  score(D,Q)  = Σ_{t∈Q} IDF(t) × ( tf(t,D)×(k1+1) ) / ( tf(t,D) + k1×(1 - b + b×|D|/avgdl) )
  k1 = 1.2, b = 0.75,  |D| = chunk 字符数
  ```

- 平滑 IDF 保证 IDF 恒为正；**df = 0 的查询词直接跳过**。
- 排序：主序 score 降序，次序 `chunkId` 字典序升序（tie-break 必须有，否则 AC-6 会挂）。
- 分数显示 3 位小数，分项贡献显示 4 位小数（允许 0.0001 级舍入差）。

#### ⑦ 与 `xhs-rag` 的算法分歧（已定案：P1）

`xhs-rag` 用的不是 BM25，它的真实打分是 `score = Σ [3×(1+ln tf_title) + 1×(1+ln tf_body)] × (1 + 命中token数/查询token数)`：
没有 IDF、没有长度归一化，多了标题权重与覆盖率因子。

本 demo 按 D9 用真 BM25。**代价**：demo 的排序结果**不能**用来推断 `xhs-rag` 的线上表现；同一 query 两边可能给出不同顺序（R1）。处置：只实现 BM25，并在页面上写明「本页结论不可外推」。

### 4.3 检索管线（v0.4 = 三遍 + 收藏夹整理）

**第一步：意图识别（🔶 模拟）**

| 意图 | 触发词示例 | 关联收藏主题 | 处理路径 |
|---|---|---|---|
| 出行决策 | 旅游/旅行/出行/去哪/玩/国庆/假期/攻略 | 云南旅游 | 关键词检索 |
| 本地美食 | 吃/餐厅/美食/日料/本帮菜/咖啡/上海 | 上海餐厅 | 关键词检索 |
| 美妆选购 | 粉底/底妆/油皮/敏感肌/护肤/防晒 | 敏感肌油皮粉底液 | 关键词检索 |
| **收藏夹整理** | 收藏/收藏夹/整理/归档 | 不限定（可带聚焦主题） | **全库聚合（不做关键词命中）** |
| 通用检索 | 以上都不命中 | — | 关键词检索 |

**第二步：检索词构建（🔶 模拟）** —— 三类来源，逐词标注：

- **原词**：query 自己切出来的多字 token（✅ 真实来源）；
- **改写词**：预置改写表把生活口语换成能命中的词，例如 国庆 → 假期/出行/旅游、好吃 → 餐厅/美食（🔶 模拟）；
- **主题词**：意图映射到的收藏主题的种子词，例如 云南 → 云南/大理/丽江/香格里拉（🔶 模拟）。

**第三步：打分（三遍策略，⑦ 混合来源）**

1. **原词精确遍**：只用 query 原词的多字 token。命中 → `tokenSource=query`（这一遍的打分来源是纯原词）。
2. **改写遍**：原词 0 命中时，改用 原词 + 改写词 + 主题词（仍是多字 token）。命中 → `tokenSource=mixed`。**这是「混合来源」的由来**。
3. **放宽遍**：仍然 0 命中时，才加入 CJK 单字（排除虚字表），结果标注「宽松命中、相关度较低」。

更靠前的一遍有命中就不进入下一遍 —— 宁可少给几条，也不让单字噪声淹没真正的匹配。

**第四步：收藏夹整理路径**（query 提及收藏时）

- 不做关键词命中，直接对全库做**真实聚合**（按主题分组、统计条数与完整性），把收藏的帖子本身作为**引用**；
- 若 query 里还带主题词（如「整理我的美妆收藏」），额外补一遍该主题的检索作为**重点引用**；
- 聚合是 ✅ 真实计算；意图判断是 🔶 模拟。

### 4.4 有 RAG / 无 RAG 对照（v0.4 新增，页面的核心价值）

- **左栏「✅ 有收藏 RAG」**：输入 = FR-9 的 prompt（含 `【用户收藏库引用】` 或整库总览）；输出 = 真实 LLM 产出，落点必须能追到收藏里的具体帖子，并带可点击引用。
- **右栏「🔶 无 RAG 基线」**：输入 = 一段**只说「用户没有提供任何私人资料」**的 prompt + 同一个问题；输出 = 同一模型的通用回答，**不给收藏、不要求出处**。
- **对照小结**：每条 query 一段**人工整理**的差异说明（页面明确标注「不是模型输出」），点出 4 个观察维度：能否落到自己的帖子 / 有没有出处可核对 / 有没有具体数字与步骤 / 有没有主动提示不可信内容。
- **诚实边界**：两段都是提前生成后内嵌的（页面不发网络请求）；两段都不含置信度 / 相似度数字。

### 4.5 数据模型与语料

**语料（v0.4）**：3 主题 × 4 条 = 12 条；10 条可用 + 2 条内容不完整。

| 主题 | 条数 | 其中内容不完整 |
|---|---|---|
| 云南旅游 | 4 | 1（图片型：正文仅 4 字符） |
| 上海餐厅 | 4 | 1（风控页：命中「请打开小红书App」） |
| 敏感肌油皮粉底液 | 4 | 0 |

**note 字段**：`noteId / url / title / text / author / theme / usable / degraded / importedAt`（`theme` 仅用于分组展示，不参与打分）。

**chunk（索引与检索的最小单位）**：

| 字段 | 来源 | 说明 |
|---|---|---|
| `chunkId` | 生成 | `${noteId}#${序号}`，序号从 0 开始 |
| `text` | 从所属 note 的 `text` 切出 | 分块结果，是 BM25 的文档 D |
| `chunkIndex` | 生成 | 块在帖子内的顺序 |
| `start` / `end` | 生成 | 在原文里的覆盖区间（用于 ③ 的覆盖区间条） |
| `dupPrefix` | 生成 | 与上一块的重叠字符数 |
| `noteId / title / author / url / theme / usable / degraded` | 继承自 note | `title` 仅展示，**不参与打分** |

**内容不完整帖子的处置**：**照常分块、照常参与检索**，命中时带标记与原因（与 `xhs-rag` 的 `index.js:310-315` 行为一致）。这也让「命中全为不完整帖子」的边界用例成立（B6）。

### 4.7 功能需求条目

> 优先级一律写「未指定」：材料中没有任何紧急程度信息。

#### FR-1 载入语料
- 描述：启动时从内嵌构造数据初始化，显示总数 / 可用 / 不完整 / 主题分组；卡片只显示**标题 + 正文字数**，点击展开正文与不完整原因。
- 验收：12 条、10 可用、2 不完整；3 主题各 4 条；卡片收起时只有标题与字数。

#### FR-4 分块（③）
- 描述：展示每条帖子的 chunk 数、覆盖区间、文本与字符数；`chunkSize`、`overlap` 可调。
- 参数约束：`chunkSize` 夹到 `[40, 2000]`；`overlap` 夹到 `[0, chunkSize-1]`；非法输入夹取并提示，**不得静默接受**。
- 验收：默认参数下每条至少 1 个 chunk，且**至少 3 条**切出 ≥2 个 chunk（实测 10/12）；去掉重叠拼接必须逐字等于原文（实测 12/12）；改小 `chunkSize` 后 chunk 数增加且保真不变；`overlap ≥ chunkSize` 被夹取并提示，页面不卡死。

#### FR-5 建索引（⑤）
- 描述：展示 N、词典大小、Σ\|D\|、avgdl、建索引耗时，以及**本次检索会用到**的每个词的 来源 / df / IDF / 倒排表（前 3 块）。
- 验收：N 与 avgdl 可人工核算复现；df 等于「含该词的 chunk 数」；df=0 的词明确标注「打分时跳过」。

#### FR-6 意图识别与检索词构建（⑥，模拟）
- 描述：展示意图（含触发词、关联主题、处理路径）与三类来源词（原词 / 改写词 / 主题词）。
- 验收：`国庆节去哪儿玩` → 出行决策、改写含 国庆→旅游；`上海有什么好吃的` → 本地美食、丢弃 `吃的`；`整理我的收藏夹` → 收藏夹整理；预置集之外的 query 按可解释规则给出，**不得留白**。

#### FR-7 检索与打分（⑦，混合来源）
- 描述：用「原词 + 改写词 + 主题词」按三遍策略打分，返回 top-5；每条展示总分、**逐词来源与贡献拆解**、命中 token、命中片段、所属帖子与出处 URL、`matchMode`、整体来源（原词 / 混合）。
- 验收：`油皮粉底液怎么选` top-1 分数可上溯到具体 token 且与公式核算一致（实测一致）；同一 query 连续两次结果完全一致；内容不完整帖子命中时带标记与原因。

#### FR-8 宽松命中与空态
- 描述：精确遍与改写遍都 0 命中时才放宽到单字（排除虚字表），标注「宽松命中、相关度较低」。
- 验收：`雪山索道` → 宽松命中 + 提示；`露营` → 明确空态文案；`的` → 无有效检索词空态，**不得**返回满屏结果。

#### FR-9 Prompt 组装（⑧，真实）
- 描述：拼出**两份** prompt 并展示、可复制：
  - 有 RAG：系统提示 → 本次意图与检索说明 → 【用户收藏库引用】（或整库总览）→【其他参考内容（非收藏库）】→ 用户问题；
  - 无 RAG 基线：只说「用户没有提供任何私人资料、不需要标注出处」+ 同一个问题。
- 验收：有 RAG prompt 的引用顺序与 ⑦ 结果顺序一致；无命中时写入明确指令（「收藏里没有找到」）而不是留空；两份 prompt 各显示 hash。

#### FR-10 决策建议与出处（⑨，真实 LLM 产出）
- 描述：两栏分别渲染有 RAG / 无 RAG 的回答；有 RAG 栏的引用可点击回到帖子卡片；附人工对照小结。
- 验收：引用可点击回帖；**不显示任何置信度 / 相似度数字**；无命中时有 RAG 栏如实说明「收藏里没有找到」；非收藏库段落单独标注。

#### FR-11 真实性全局标识
- 描述：每个环节标题旁显示四类标记之一；顶部提供图例，写明「🔶 的结果是预置的，不是计算出来的」。
- 验收：7 个环节标记 100% 覆盖且与 4.2 表一致；图例包含四类标记的解释与「内嵌 ≠ 当场调用」的说明。

#### FR-12 事件记录面板
- 描述：页内可展开面板，按时间倒序记录事件，支持导出 JSON。
- 验收：导出文件包含本页 8 类事件（本页真实触发过的）；刷新清零。

#### FR-13 预置问题一键填入
- 描述：5 个预置问题 + 4 个边界复现按钮；点击**只填入输入框，不自动执行**。
- 验收：按钮文案与数据源 `presetQueries` / `boundaryReproduction` 一致；点击后输入框被填入且未触发检索。

#### FR-14 有 RAG / 无 RAG 对照（v0.4 新增）
- 描述：首屏「最终决策建议」内左右两栏并排展示两段回答，并在下方给出人工对照小结。
- 验收：两栏各自标注来源与 `promptSha`；右栏明确写出「这栏没有任何出处」；对照小结标注「人工整理，不是模型输出」。

#### FR-15 真实 LLM 产出的完整性与可核对（v0.4 新增）
- 描述：⑨ 的两段回答默认使用内嵌的真实模型输出；页面用当前构建的 prompt 重算哈希，**一致才展示**。

#### FR-16 模块折叠与说明符号（v0.4 新增）
- 描述：每个模块可展开/收起，收起时表头显示关键数字；解释性长文案收进 ⓘ；顶部提供全部展开 / 全部收起。

## 6. 埋点方案

**前提**：单文件静态页**没有服务端**，不存在生产意义上的上报。「埋点」只有两个用途：① 留下 G1/G2/G5 的验证记录；② 让「我点过什么」可回溯。**不能用于漏斗分析，不能跨人聚合。**

本页共 **8 类事件**（PRD 原列 10 类，去掉随 ① 删除的 `link_parse` 与随理解自测删除的 `quiz_submit`）：

| 事件名 | 触发时机 | 关键参数 | 用途 |
|---|---|---|---|
| `demo_load` | 页面初始化完成 | 笔记数、可用数、不完整数、主题数、内嵌回答数、是否离线 | G1 |
| `index_build` | 建索引完成 | note 数、chunk 数、N、词典大小、avgdl、耗时 ms | G1 / FR-5 |
| `query_submit` | 提交检索 | query、意图、queryTokens、丢弃的 bigram、matchMode、pass、tokenSource、是否收藏夹整理、是否预置 | G1 / FR-6 |
| `query_result` | 检索返回 | top-k 的 (chunkId, score, matchedTokens, sources)、命中数、是否降级命中、全库聚合规模 | G1 / FR-7 |
| `prompt_preview` | 展开 prompt 预览 | 有 RAG 的引用段数与字符数、无 RAG 的字符数 | FR-9 |

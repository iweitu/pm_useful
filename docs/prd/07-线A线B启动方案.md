## 1. 一个必须先纠正的认知（否则线 A 会做重）

我在规划 v0.5 里把知识库的"检索"想重了。对**单人、几十到几百条**的知识库来说：

| 方案 | 成本 | 什么时候才需要 |
|---|---|---|
| **文件检索（先做）**：Markdown + 目录约定 + frontmatter + `grep`，由 agent 读文件后归纳 | **几乎为 0**（不需要新组件） | 【已定】**现在就用这个** |
| 向量检索 / RAG 管线 | 3~8 人天 + 持续维护 | 条目 >300 条且文件检索明显找不到时才考虑 |

**理由**：PRD 规划里写"检索问答（FR-3）"时，我没有说清检索靠什么实现 —— 这会让工程同学默认上向量库。对单人知识库，**目录 + frontmatter + grep + agent 阅读**已经能覆盖绝大多数提问，而且**可审计**（你能看到它读了哪个文件），这在 D-13 红线之下比"相似度 0.82"更可信。

→ 已同步修正主文档（新增 D-23）。

## 2. 线 B 启动方案

### 2.1 认清起点（基于真实文件，不是想象）

| 事实 | 依据 |
|---|---|
| `prd-partner` = 一个 bundle 补丁，只有 **3 个文件**：`cordis.patch.yml` / `package.json` / `README.md` | `agents/prd-partner/` 目录列表 |
| 它**已经挂载了 `skill` 工具**，所以 6 个技能（prd-writer / prd-review / competitor-analysis / priority-scoring …）**本来就可用** | `agents/prd-partner/README.md` 的工具对比表 |
| 它**没有**命令执行、子 agent、workflow、plan mode | 同上（那 5 行"不挂载"） |
| 装到 profile 的是**副本不是符号链接**，**改源码必须手动重新同步**，否则改了不生效 | README「当前安装状态」+「局限」第 3 条 |
| 安装副本时 `install_bundle` 会对同一 `file:` 依赖返回 `ambiguous-install` / `changed:false`（pnpm 报 Already up to date） | README「v1.1.0 的更新方式」 |

**结论**：线 B 的工作量几乎全在**人格文本**（`cordis.patch.yml` 的 `persona.config.prefix`）上，**不需要新增插件行、不需要改包名** —— 这直接消掉了我原先估的风险（"包名必须在可加载清单内"）。

### 2.2 要改的 4 处（逐处给验收）

| # | 改哪里 | 改成什么 | 验收 |
|---|---|---|---|
| **B-1** | `cordis.patch.yml` → `persona.config.prefix` | 新增「技能触发规则」：**什么时候必须调** `competitor-analysis`（提到竞品/对手/对比时）、**什么时候必须调** `priority-scoring`（出现 ≥3 条候选需求或出现排序争议时） | 用一句话"帮我分析下这几个竞品"跑一次，输出里出现功能矩阵且**未验证项没被写成结论**（FR-9） |
| **B-2** | 同上 | 在 12 节骨架里补 **「三层分区」一致性**：产出 PRD 时必须标注该需求属 T1/T2/T3，且**含公司业务事实的 PRD 只能存公司内飞书** | 让它对一个含公司产品的需求出 PRD，它必须**先提示分区风险**而不是直接成稿（对应 FR-17 的行为前移） |
| **B-3** | 同上 | 保留并强化既有规则：一轮 ≤3 问且带默认答案、只改必要章节、结尾三行、**收尾给"距可评审还差什么"** | 跑一次修改任务，确认它只动了必要章节且结尾三行齐全 |
| **B-4** | `README.md`「安装状态」 | 记录本次版本号、同步命令、SHA256 校验结果、GUI 亲眼确认结论 | 文档里能查到"这次装的是什么、怎么回滚" |

### 2.3 执行步骤（含那个必踩的坑）

| 步 | 动作 | 谁做 |
|---|---|---|
| 1 | 改 `agents/prd-partner/cordis.patch.yml` 的人格文本（B-1~B-3） | **需要动手的一方**（属实现层，我不改文件） |
| 2 | 静态校验：`check.mjs` + `verify-agent-bundle.mjs`（不需要运行中的 Host） | 同上 |
| 3 | 同步到 profile 副本（**坑**：`install_bundle` 会报 Already up to date，必须按 README 的手动 `Copy-Item` 方式同步，先备份） | 同上 |
| 4 | SHA256 校验源文件与副本一致 | 同上 |
| 5 | **GUI 亲眼确认**：设置 → Agent preset → 需求伙伴卡片存在、工具列表里**没有** `pwsh`/`bash` | **只能你做** |
| 6 | 冒烟测试：用新契约跑一份真实 PRD，检查 4 处改动是否生效 | 你做 |

### 2.4 失败预案

| 现象 | 处理 |
|---|---|
| 卡片不出现 | 先刷新页面（profile manifest 由 HMR 重组，通常不必重启）；仍不出现再重启 Harness |
| 卡片出现但标加载失败 | 点「查看配置」看声明原文，按诊断定位哪一行被拒（**注意：不要改内置 preset，要按行 id 覆盖**） |
| 人格太长导致 agent 行为变差（开头几轮不遵守契约） | 人格文本按"必须先做 vs 建议做"分层，把输出契约的 3 条硬规则提到最前面，其余压缩 |
| 改了没生效 | 90% 是没同步副本 —— 回到 2.3 第 3 步，别怀疑人格写错 |

## 3. 线 A 启动方案

### 3.1 目标（第一周只做这一件事）

**让知识"装得进去、找得到、可审计"** —— 不做采集自动化、不做向量检索、不做问答界面。

### 3.2 目录结构（【已定】，可照抄）

```
knowledge-base/            ← T1 本地区（唯一允许外部 LLM 的知识区）
  00-inbox/                ← 唯一入口：任何素材先扔这里，不要求格式
  10-method/               ← 方法论：怎么写 PRD / 怎么排优先级 / 怎么讲故事
  20-research/             ← 公开资料：竞品公开信息、行业报告、公开文档
  30-domain/               ← 领域知识（不含公司业务事实）
  40-decision/             ← 决策记录（D-x 的长期落点）
  99-review/               ← 每周复盘记录（含 G-8 时间日志）
```

**每条条目的固定形态**（frontmatter + 正文）：

```markdown
---
zone: T1                 # 必填：T1 / T3；T2 不允许出现在本库
topic: <主题>
source: <来源链接或"个人经验">
date: 2026-10-07
confidence: 高|中|低
related: [ <关联条目> ]
status: 草稿|已审核
---

## 结论（3 句以内）
## 依据 / 原文出处
## 适用边界（什么时候这条不成立）
```

### 3.3 起手三步（第一周）

| 步 | 动作 | 产物 | 时长 |
|---|---|---|---|
| **A-1** | 建目录 + 把上面 4 个模板文件落地（条目模板、采集说明、分区判断清单、复盘模板） | 一个能直接往里写的库 | 1h |
| **A-2** | **手填 3 条**，不许跳过。建议：① 那篇现成的 `knowledge/一文完全读懂RAG.md` 摘要成 1 条；② 一条你自己的 PRD 写法；③ 一条踩坑记录 | 3 条已审核条目 | 1.5h |
| **A-3** | 用 agent 跑一次真实使用：**先 `grep` 找条目、再基于条目回答**，检查是否给得出准确引用 | 一次带引用的问答记录 | 0.5h |

**为什么 A-2 必须手工做**：这一步同时验证了"条目模板是否好用"。如果手填 3 条就觉得麻烦，**这套模板在你现在的场景下就是错的**——这个结论花 1.5h 得到，比花 3 天写完采集自动化再发现要便宜得多。

### 3.4 第二周再做的（不要提前）

| 动作 | 前置条件 |
|---|---|
| 建 `knowledge-agent` 的 preset（只读知识库 + 只写 `00-inbox` 与条目 + 拒收公司资料 + 不静默入库） | A-1~A-3 完成，且手填过程没有明显摩擦 |
| 采集入口半自动化（一句话进 inbox → agent 出结构化条目草稿 → 我确认） | 同上 |
| `zone_blocked` / `kb_ingest` / `time_log` 三个埋点落地 | 同上 |

### 3.5 第一周验收（对应主文档 AC-5/AC-6/AC-13/AC-14）

| 验收 | 标准 | 方式 |
|---|---|---|
| AC-5′ | 5 份素材投入 → **≥4 份**产出合规条目（结构 + frontmatter 齐全） | 👤 人工点数 |
| AC-13′ | 每一条都能在目录树上找到**唯一归属**，无"未分类" | 👤 人工点数 |
| AC-6′ | 10 个问题：回答要么带引用、要么明说无命中；**带引用但引用不存在 = 0** | 👤 人工核对（第一周靠人眼，靠脚本是第二周的事） |
| AC-14′ | 构造 10 份含公司特征的输入 → **10/10 被拒收** | 👤 人工（用真实的公司域名/姓名/代号构造，**测试完即删**） |

> AC-14′ 的测试数据必须在 T3 假数据区构造，**用完立即删除**。这是第一周唯一有合规风险的动作，别顺手留下一份"测试用"的真会议纪要。

### 3.6 失败预案

| 现象 | 处理 |
|---|---|
| 手填 3 条就懒得填 | **判定：模板太重**。把 frontmatter 砍到 3 个字段（zone / topic / source），重试一次；再不行就把条目降级为"一句话 + 出处" |
| 条目很快过时、没人更新 | **判定：这些知识不值得沉淀**。转向 S-1 的真实用途 —— 只沉淀"会重复用到的方法"，放过一次性信息 |
| 你发现真正想存的知识都在公司飞书里 | 这**不是线 A 的失败**，是 Q-6 的结构性结论（知识都在公司内）。此时把线 A 收窄为"只装方法论"，并把重心移到公司侧半自动链路（FR-18~20） |
| 到第 6 周条目 <20 条 | 触发 R-13 预案：**判定设计失败**，停止加功能，重新评估是否值得继续（不要用"再加个自动采集就好了"续命） |

## 4. 并行不冲突的保障（双线怎么不打架）

| 冲突点 | 规避方式 |
|---|---|
| 两条线都改 `knowledge/` 目录 | **线 B 不改知识目录**（它只改 `agents/prd-partner/` + 自己的 README） |
| 两条线都要"记录进度" | `99-review/` 是唯一记录点；`docs/prd/` 下的规划文档只由线 A 的成果触发更新 |
| 时间被单线吃光 | 显式约定：**线 B 是"当天可完成"的小活，先做**；线 A 是长期主线，每次投入 ≥1h 才有意义（碎片 15 分钟不启动线 A） |
| 埋点工作重复 | 埋点统一由线 A 落地，线 B 复用（`prd_draft_done` / `prd_self_review` 已在线 A 的事件表里） |

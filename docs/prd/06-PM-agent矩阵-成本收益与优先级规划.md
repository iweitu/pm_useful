## 一页需求卡

| 维度 | 内容 |
|---|---|
| 目标 | 在**一个季度**内，把 6 个自提项目按「先地基后上层」的顺序落到一个可部署的 GitHub 仓库，使其中 **≥3 项进入日常使用**（周使用 ≥2 次），且**公司资料全程不出内网** |
| 用户 | 资深互联网 PM（本人，单人使用）；收益外溢对象为同事与群成员（非直接用户，无账号） |
| 场景 | 会议后整理纪要 → 群消息待办提取 → 通用知识沉淀 → 周度 OKR/需求梳理 → 竞品调研与 PRD 撰写 → demo 验证 → 用户故事论证必要性 |
| In | 6 个项目的成本/收益/优先级评估；GitHub 仓库结构与部署方案；7 个补充项目建议；三层分区模型（本地 / 公司内 / 假数据） |
| Out | ① 本次**不写任何实现代码**（需求侧交付）；② 不替公司做合规审批与权限申请；③ **不评估公司是否有可用内网 LLM**（→ Q-4，决定公司侧能力是"接入"还是"放弃"） |
| 验收 | AC-1 每个项目都能在正文找到成本区间、收益类型、优先级名次；AC-2 每个成本数字都能追到第 7 节依据或标注【待确认】；AC-3 「下一轮做什么」能追到 D-1/D-14 与第 5 节场景；AC-4 仓库方案不泄露任何公司业务内容（三仓库隔离可核）；**AC-13 每个 FR 都有明确的分区归属（本地 / 公司内 / 假数据）** |
| 未决 | Q-3 每周可维护时间预算（用户答复：暂不知道 → 改为 D-14 的测量法）；Q-5 公司飞书自建应用与群消息权限能否获批、本地跑机器人是否触发合规审查（→ FR-5、R-11）；Q-6 第 2 问：公司侧素材的形态与数量（→ 用户故事项目能否启动） |
| 一句话结论 | 6 个项目**不是平级清单而是有依赖的图**：知识库是唯一前置项；叠加「公司内容不出内网」这条硬约束后，**个人机器人被砍成"零 LLM 的待办提取器"**，公司知识问答整体不自己做、改接公司已有服务 |

| 8 | **用户答复 Q-4：公司有 AI 功能，但无开放 API / 拿不到凭证** | 用户 2026-10-07 答复（本文档输入） | 这是**"次优但可做"**的结果：公司侧项目不死，但形态从"自动化集成"变成"半自动 + 标准化"（→ D-18）。也意味着 **"自动化"这条路在公司侧被证否，价值要靠"把提问变规范"来兑现** |
| 9 | **用户答复 Q-5：能建自建应用 + 能批消息权限** | 用户 2026-10-07 答复（本文档输入） | 机器人**接入路径打通**（→ D-21）：v2 可读群消息。但**价值仍受 D-13 压制**（不允许送外部 LLM），所以能力是"提取与准备"，不是"替我回答" |
| 10 | **用户答复 Q-3：每周可投入 5 小时以上** | 用户 2026-10-07 答复（本文档输入） | 时间预算是排序之外唯一的真实约束。5h/周 ≈ **双线并行的下限**：够维持一条主线（4~6 周）加一条穿插线，**不够同时启动多个新项目** |

**问题陈述**：我不缺「能做的 agent」，缺的是**判断先做哪个、以及哪些做了也不会被日常使用**的依据 —— 现有 6 个项目彼此有依赖（知识库是全部下游的输入），但被当成平级清单来规划，会导致精力分散、每个都半成品。

**v0.2 追加的问题陈述**：我原本按"外部 LLM 可用"设计整套方案，但公司环境不允许把工作内容送外部 LLM。这意味着**同一批 agent 在公司场景下等于不存在** —— 真正要解决的不是"能力不够"，而是**「知识分两处、能力分两套」的架构问题**：通用知识在本地、公司资料在公司内飞书，两者不能被同一个检索链路合并（D-12）。

## 6.5 三层分区模型（v0.2 新增，D-12 的落地表）

> 这张表是本次改动里**最重要的一张**：它把"合规约束"变成"工程约束"，让每个 FR 都有明确归属，避免开发时把公司资料误接进外部模型。

| 分区 | 存什么 | 存哪 | 谁能读 | 能用外部 LLM 吗 | 对应 FR |
|---|---|---|---|---|---|
| **T1 本地区** | 通用知识、开源资料、RAG/PRD 等方法论、公开竞品信息、我个人的通用经验（不含业务事实） | 本地 Markdown，Git 版本化；进私有知识库仓（D-8） | 本机 agent | ✅ 可以 | FR-1~3、FR-9~11、FR-12~14（方法论态） |
| **T2 公司区内** | 公司业务资料、会议内容、同事信息、群消息 | **只能存公司内部飞书文档**（Q-1 答复） | 公司内模型 / 公司内已有一问一答能力 | ❌ **绝对不可以** | FR-5（待办提取，零 LLM）、公司侧纪要归档 |
| **T3 假数据区** | demo 用的构造数据、脱敏示例、演示语料 | 本地，但**独立目录 + 显式标注**（如 `demo/*/data/`） | 本机 agent | ✅ 可以 | FR-15~16 |

**分区三条铁律**：

| # | 铁律 | 违反后果 |
|---|---|---|
| 1 | **禁止跨区检索**：一次提问不允许同时命中 T1 与 T2 | 跨区合并 = 把公司资料拼进外部 LLM 上下文，等同违规 |
| 2 | **T3 禁止与 T1/T2 混放**：假数据必须能被一眼识别 | 演示数据被当成真实业务结论引用（这是最隐蔽的错误） |
| 3 | **T2 的入口只有一个**：公司内飞书文档 | 出现第二个入口即无法审计，红线失守 |

**T2 的已知限制（必须提前接受）**：

| 限制 | 说明 |
|---|---|
| 我的本地 agent**无法检索** T2 | 除非公司提供 API 且我获得授权（Q-4 / Q-5 未定） |
| T2 的 AI 能力**不是我能决定的** | 依赖公司是否已部署内网 LLM（D-13、D-17） |
| 工作流要**人工分段** | 场景 4/6 需要我在两区之间手动搬运"框架 ↔ 内容"，多一步操作（这是 D-12 的代价，已写入决策表） |

> 全部耗时与收益数字均为 🔶 估算或【推断】。**没有任何一项是实测数据** —— 这是本文档最重要的诚实声明。要变成实测，只需先做第 12 节的基线记录（= 1 天工作量）。
>
> **v0.2 补充**：G-8（可投入时间）在用户答复"暂不知道"后**保持为【待确认】而不是我给一个数**。理由：时间预算是排序公式的分母，猜一个分母等于让整张排序表失去意义。

## 11. 交付、回滚、分发 + 风险（R-x）

### 11.1 GitHub 三仓结构（D-8、D-9）

| 仓库 | 可见性 | 放什么（分区） | 绝对不放 |
|---|---|---|---|
| `pm-useful`（公开） | Public | skills、agents、prompts、tools、demo（**T3 假数据**）、通用 knowledge（**T1**）、docs | 公司业务内容、同事姓名、真实测试数据、公司内文档链接、**任何 T2 内容** |

| `pm-useful-knowledge`（私有） | Private | **T1 知识库本体**（条目 + 索引） | **T2 内容一律不入仓**（T2 只存在公司内飞书，Q-1 已定） |

> **v0.2 关键澄清**：把 T2 放进"私有仓"**仍然违规**。私有只是访问控制，不等于"不出内网"。因此上面三仓里**没有任何一格是给 T2 准备的** —— T2 的载体只有公司内部飞书文档一个（D-12 铁律 3）。

同步与部署：

| 场景 | 做法 |
|---|---|
| 公司 / 个人双环境 | `git clone` 公开仓 → 私有仓单独 `git clone` 到不纳入公开仓的子目录（如 `.private/`，已 gitignore） |
| 一键可用 | 一个 `bootstrap` 脚本：同步 `skills/` 到扫描根（`~/.dsh/skills` 或项目级 `.dsh/skills`）、装 profile bundle、打印自检结果 |
| 回滚 | 每个 skill / agent 独立目录 + git tag；出问题 `git revert` 单目录即可，不整仓回滚 |
| CI | 跑已有 `tools/verify-agent-bundle.mjs` 与 demo 验证脚本；**不接入任何公司内容校验** |

# PRD 评审

目标是**在评审会上被问倒之前，先把问题找出来**。重点不是评价文档写得好不好，而是找出会让开发返工、让上线后无法验证、让决策依据不成立的具体缺陷。

## 输入处理

接受以下任一输入：

- 用户粘贴的 PRD、需求文档正文
- 用户指定的本地文档
- 截图或转述的方案要点（信息不全时说明哪些判断受限于信息量）
- 已有 PRD 加用户特别关注的问题（如"重点看埋点""领导特别在意成本"）

文档不完整时，**就已有内容评审**，缺失的章节按"缺失项"归类输出，不要因文档不全而拒绝评审。

## 评审流程

1. **通读并还原意图**：先用一句话复述"这份 PRD 想做什么、给谁做、解决什么问题"，作为后续判断的基准。
2. **按维度逐项检查**：走下文《检查维度》，每个维度都必须给出结论，不能因为看起来没问题就跳过。
3. **交叉一致性检查**：指标 ↔ 埋点、功能 ↔ 验收、范围 ↔ 需求条目、目标 ↔ 功能，任一处对不上就是一个问题。
4. **定级**：按严重程度分 Blocker / 重要 / 建议三档，见《定级规则》。
5. **给可执行建议**：每条问题都给出具体怎么改，而不是只说"这里不清楚"。

## 检查维度

| 维度 | 要找的问题 |
|---|---|
| 问题与背景 | 是否把功能当需求；是否说清现状与痛点；有无数据支撑或明确标注数据缺失 |
| 目标与指标 | 指标是否可衡量；有无基线；目标与需求是否真能建立因果关系；有无反向指标（如改留存却伤体验） |
| 范围 | 有无明确 Out of Scope；范围是否与后续需求条目一致；有无夹带未声明的需求 |
| 用户与场景 | 场景是否具体到可复现；是否只描述了理想路径 |
| 功能需求 | 是否可独立验收；描述是否含混（"优化""支持一下""体验更好"）；粒度是否一致 |
| 边界与异常 | 空数据、超限、并发、权限、超时、重复提交、离线、弱网、极端值是否覆盖 |
| 埋点 | 事件能否反推指标；命名与参数是否规范；有无漏埋、重复埋、埋了不用的点 |
| 灰度与回滚 | 有无灰度范围与放量节奏；回滚条件与方式是否明确；脏数据如何处理 |
| 依赖与风险 | 跨团队依赖是否列明并确认；有无排期风险、合规风险、外部接口风险 |
| 验收标准 | 是否可验证；是否覆盖边界与异常；由谁在什么环境验证 |
| 成本与收益 | 投入产出是否说得通；有无更小的验证方案（如先做实验或人工兜底） |

## 定级规则

- **Blocker**：不解决就无法开发或上线后会出事故。例：目标不可衡量导致无法判断成败、关键边界未定义、埋点无法支撑验证、无回滚方案。
- **重要**：会导致返工或评审争议，但不阻塞开发。例：Out of Scope 缺失、验收标准不可验证、依赖未确认。
- **建议**：提升文档质量或决策质量。例：结构顺序、表述精度、可补充的背景信息。

定级只看**后果严重程度**，不因作者身份或文档篇幅调整。无法判断后果时，说明依据不足并归入"需进一步确认"。

## 输出格式

先给一句总体结论（能否进入评审、必须解决几项），再输出问题清单：

```markdown
## 总体结论
<一句话：可以进入评审 / 需先补齐 N 项 Blocker 再评审>

## 问题清单

| # | 级别 | 位置 | 问题 | 影响 | 建议改法 |
|---|---|---|---|---|---|
| 1 | Blocker | 第 2 节 | 目标写"提升活跃"，无指标与基线 | 上线后无法判断成败 | 改为"次日留存 +Xpt，基线 Y"，基线需补数据 |

## 做得好的地方
- <只写确实成立的部分，用于保留，不要凑数>

## 需进一步确认
- <信息不足无法定级的事项，注明需要什么材料>
```

问题清单按 Blocker → 重要 → 建议排序；同一级别内按文档出现顺序排，便于作者对照修改。

## 质量检查

输出前确认：

- 每条问题都具体到**位置**，作者能直接定位。
- 每条问题都给了**改法**，不是只指出"不清楚"。
- 定级有依据，且没有为了显得严格而滥用 Blocker。
- 没有虚构文档里不存在的内容，或把"我可以这样理解"写成"文档说了"。
- 检查维度全部走过一遍，缺失项已作为问题列出。
- "做得好的地方"若确实没有，直接省略该节，不硬凑。

## 示例

输入：一份写着"目标：提升用户活跃度，做法：增加签到功能，验收：功能正常可用"的 PRD。

输出要点：

- Blocker：目标无指标与基线，验收"功能正常可用"不可验证，二者叠加导致上线后无法判断成败。
- 重要：未写 Out of Scope（签到是否含补签、是否发奖未界定）；未写埋点，无法验证活跃变化。
- 重要：未定义边界——跨天时区、补签次数上限、并发点击、奖励发放失败如何处理。
- 建议：补充签到与活跃之间的因果假设（连续签到是否真能提升活跃），建议先小流量实验验证。
- 总体结论：需先补齐 3 项 Blocker 再评审。
